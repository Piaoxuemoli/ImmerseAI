# ImmerseAI 架构优化方案

> 基于代码深度分析制定的系统优化路线图
> 分析日期：2026-03-27

---

## 一、核心架构概览

```
┌─────────────────────────────────────────────────────────┐
│  Renderer (React + Zustand + Vite)                      │
│  src/features/{bookshelf,chat,reader,persona,settings}  │
└────────────────────┬────────────────────────────────────┘
                     │ IPC (contextBridge)
┌────────────────────▼────────────────────────────────────┐
│  Main Process (Electron 28 + TypeScript)                 │
│  ├── mcp-manager.ts   MCP 客户端 (Stdio 传输)            │
│  ├── rag-handler.ts   RAG 管道 (Chunk → Embed → Search)  │
│  ├── llm-handler.ts  OpenAI 流式聊天                     │
│  └── ipc-handlers.ts  IPC 通道路由                       │
└─────────────────────────────────────────────────────────┘
```

**技术栈**
- 运行时：Electron 28
- 前端：React 18 + TypeScript + Vite 5
- 样式：TailwindCSS 3 + shadcn/ui (Radix UI)
- 状态：Zustand 4 + persist 中间件
- Agent 协议：@modelcontextprotocol/sdk (Stdio)
- RAG Embedding：@huggingface/transformers (all-MiniLM-L6-v2)
- 向量检索：@orama/orama (内存 BM25)
- LLM：OpenAI SDK (OpenAI 兼容 API)
- 动画：framer-motion 11

## 二、问题诊断

### 2.1 IPC 通信层

| 问题 | 严重程度 | 位置 | 描述 |
|------|---------|------|------|
| `[DONE]` 字符串哨兵脆弱 | 🔴 高 | `llm-handler.ts:141` | 若模型输出 `[DONE]` 文本，渲染进程会提前终止流 |
| `rag:ingest` 为单向投递 | 🟡 中 | `ipc-handlers.ts:167` | 使用 `ipcMain.on` 而非 `handle`，错误依赖单独事件通道 |
| 缺少健康检查通道 | 🟡 中 | - | 渲染进程无法检测主进程是否卡死 |

### 2.2 MCP 集成

| 问题 | 严重程度 | 位置 | 描述 |
|------|---------|------|------|
| 无连接超时 | 🟡 中 | `mcp-manager.ts:215` | `client.connect()` 可能无限阻塞 |
| 递归重试可简化 | 🟢 低 | `mcp-manager.ts` | 3 层递归改迭代更清晰 |
| `lastModified` 被覆盖 | 🟢 低 | `mcp-manager.ts:108` | MCP 服务器返回的时间戳被忽略 |

### 2.3 RAG 管道

| 问题 | 严重程度 | 位置 | 描述 |
|------|---------|------|------|
| 无取消支持 | 🔴 高 | `rag-handler.ts` | 用户中途离开页面，索引仍在后台浪费计算 |
| 后台升级存在竞态 | 🟡 中 | `rag-handler.ts:375-377` | `saveCache()` 和 `oramaIndexCache.delete()` 之间可能被搜索命中 |
| 批处理大小保守 | 🟡 中 | `rag-handler.ts` | `BATCH_SIZE=32`，可提升至 64+ |
| 内存缓存无 LRU | 🟢 低 | `rag-handler.ts` | 仅按数量限制，未考虑单个索引大小 |
| `chunkParagraphs()` 同步阻塞 | 🟢 低 | `rag-handler.ts` | 大书籍可能导致主线程卡顿 |

### 2.4 LLM 处理

| 问题 | 严重程度 | 位置 | 描述 |
|------|---------|------|------|
| `[DONE]` 哨兵问题 | 🔴 高 | `llm-handler.ts` | 同 IPC 问题 |
| 无请求取消机制 | 🟡 中 | `llm-handler.ts` | HTTP 请求本身无法中止 |
| API Key 轮换问题 | 🟢 低 | `llm-handler.ts` | 缓存的 client 不会自动刷新 |
| `stream: false` 未实现 | 🟢 低 | `llm-handler.ts` | 类型定义了但代码未使用 |

### 2.5 状态管理

| 问题 | 严重程度 | 位置 | 描述 |
|------|---------|------|------|
| `indexingProgress` 从不清理 | 🟡 中 | `store/index.ts` | 动作存在但从未调用 |
| 无乐观更新模式 | 🟢 低 | `store/index.ts` | 操作失败时状态与实际不一致 |
| 无日志中间件 | 🟢 低 | `store/index.ts` | 状态转换难以调试 |

## 三、优化方案（分阶段）

### 阶段一：核心稳定性修复（高优先级）

#### R-01：用完成事件替换 `[DONE]` 哨兵

**现状**：`llm-handler.ts` 发送 `'llm:chat-chunk', '[DONE]'`，渲染进程字符串比对判断结束。

**问题**：若模型真实输出 `[DONE]` 文本，渲染进程错误终止。

**方案**：引入专用完成事件通道。

```typescript
// electron/main/llm-handler.ts 新增
// 在流结束时发送
event.sender.send('llm:chat-complete', {
  totalDuration: Date.now() - startTime
})

// electron/preload/index.ts 新增暴露
llm: {
  onChatComplete: (callback: (data: { totalDuration: number }) => void) => {
    ipcRenderer.on('llm:chat-complete', (_, data) => callback(data))
  }
}

// src/shared/hooks/useLlmStream.ts 改造
// 移除字符串比对逻辑，改为监听完成事件
```

**影响范围**：`llm-handler.ts`、`preload/index.ts`、`useLlmStream.ts`、`ChatInterface.tsx`

**工作量**：小

---

#### R-02：MCP 连接添加超时

**现状**：`mcp-manager.ts` 的 `connect()` 无超时控制。

**方案**：

```typescript
// mcp-manager.ts
private async connectWithTimeout(timeoutMs = 10000): Promise<void> {
  await Promise.race([
    this.client.connect(this.transport),
    new Promise((_, reject) =>
      setTimeout(() => reject(new Error('MCP connection timeout')), timeoutMs)
    )
  ])
}
```

**工作量**：小

---

#### R-03：RAG 管道添加 AbortSignal 支持

**现状**：索引操作无法取消。

**方案**：

```typescript
// rag-handler.ts
async function ragIngest(
  contentHash: string,
  content: string,
  signal?: AbortSignal  // 新参数
): Promise<void> {
  const chunks = chunkParagraphs(content)
  for (let i = 0; i < chunks.length; i += BATCH_SIZE) {
    if (signal?.aborted) throw new Error('Cancelled')
    const batch = chunks.slice(i, i + BATCH_SIZE)
    await embedBatch(batch)
  }
}

// ipc-handlers.ts
ipcMain.handle('rag:ingest', async (event, { contentHash, content }) => {
  // 将 AbortSignal 传入
})
```

**工作量**：中

### 阶段二：性能优化（中优先级）

#### P-01：Embedding 模型预热

**现状**：首次搜索时才加载模型，造成明显延迟。

**方案**：在 MCP 连接成功后、用户浏览书架时，闲时预热。

```typescript
// electron/main/index.ts
// MCP 连接成功后
mcpManager.onConnect(() => {
  // 闲时 5 秒后预热 embedding 模型
  setTimeout(() => {
    ragHandler.prewarm?.()
  }, 5000)
})
```

**工作量**：小

---

#### P-02：增大批处理大小

**现状**：`BATCH_SIZE = 32` 保守。

**方案**：提升至 64，并监控 CPU 使用率。

```typescript
// rag-handler.ts
const BATCH_SIZE = 64  // 从 32 提升
```

**工作量**：微小

---

#### P-03：`chunkParagraphs()` 优化

**现状**：使用 `+=` 字符串拼接，效率低。

**方案**：

```typescript
// 改前
let chunk = ''
for (const para of paragraphs) {
  chunk += para + '\n'
  if (chunk.length >= targetSize) { chunks.push(chunk); chunk = '' }
}

// 改后
const parts: string[] = []
for (const para of paragraphs) {
  parts.push(para)
}
const full = parts.join('\n')
// 然后按需分割
```

**工作量**：小

---

#### P-04：Orama 缓存 LRU 策略增强

**现状**：仅按数量 `MAX_ORAMA_CACHE = 5` 限制。

**方案**：改为按内存估算或访问频率。

```typescript
// rag-handler.ts
interface CacheEntry {
  index: OramaIndex
  lastAccessed: number
  sizeEstimate: number
}
```

**工作量**：中

## 四、错误处理增强

### 现状问题

RAG 搜索错误静默返回空结果 `[]`，无法区分"无结果"和"出错"。

### 方案：统一错误事件通道

| 操作 | 当前 | 优化后 |
|------|------|--------|
| `rag:ingest` | `rag:ingest-error` 事件 | 保持 + 添加 `rag:ingest-complete` |
| `rag:search` | 异常直接抛出 | 增加 `rag:search-error` 事件 |
| `llm:chat` | `llm:chat-error` 事件 | 保持 + `llm:chat-complete` 事件 |
