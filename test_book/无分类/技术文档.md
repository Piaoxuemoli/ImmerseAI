# ImmerseAI 技术文档

## 项目简介

ImmerseAI 是一款 Local-First 的沉浸式阅读与角色扮演 Agent 桌面应用。它通过 MCP (Model Context Protocol) 连接本地书库，利用端侧 RAG 技术理解书籍内容。

## 核心特性

### 1. 本地优先架构

所有数据完全本地化，保护用户隐私：

- 书籍文件存储在本地文件系统
- 向量索引使用 userData 目录持久化
- 仅在 LLM API 调用时有网络请求

### 2. RAG 引擎

基于主进程的向量化检索系统：

```typescript
// 使用 Transformers.js 进行向量化（q8 量化，本地离线）
embeddingPipeline = await pipeline('feature-extraction', 'Xenova/all-MiniLM-L6-v2', {
  dtype: 'q8',
  local_files_only: true,
})

// Orama 作为混合搜索引擎（BM25 词法 + 向量语义）
const db = await create({
  schema: {
    text: 'string',
    paragraphIndex: 'number',
    offset: 'number',
  },
})
```

### 3. 智能角色扮演

用户可以基于书籍内容创建角色，与其进行自然对话。角色的回答基于书中的真实内容，通过 RAG 检索相关段落，并附带原文引用角标可跳转至原文。

## 技术栈

- **前端**: React 18 + TypeScript + TailwindCSS
- **桌面框架**: Electron 28
- **状态管理**: Zustand + persist 中间件
- **向量化**: @huggingface/transformers (all-MiniLM-L6-v2, ONNX q8)
- **向量/全文数据库**: Orama（BM25 + cosine 混合）
- **LLM**: OpenAI 兼容 API（支持任意 provider）
- **MCP**: @modelcontextprotocol/sdk + server-filesystem

## 系统架构

```
渲染进程 (React)
    │  window.electronAPI (contextBridge)
    ↓
预加载脚本 (Preload)
    │  ipcRenderer.invoke / ipcRenderer.send
    ↓
主进程 (Electron Main)
    ├── McpManager    → MCP Filesystem Server (子进程 stdio)
    ├── RagHandler    → Orama + Transformers.js (本地模型)
    └── LlmHandler    → OpenAI SDK (网络请求)
```

## 模块一：整体架构与技术选型

### 1.1 Electron 三进程模型

Electron 应用由三个相互隔离的执行环境组成：

```
┌─────────────────────────────────────────────┐
│           主进程 (Main Process)               │
│  - Node.js 完整能力：fs、crypto、子进程        │
│  - 管理应用生命周期、BrowserWindow            │
│  - 运行 McpManager、RagHandler、LlmHandler   │
│  - 文件：electron/main/index.ts              │
└──────────────┬──────────────────────────────┘
               │ IPC (ipcMain / ipcRenderer)
┌──────────────▼──────────────────────────────┐
│          预加载脚本 (Preload)                  │
│  - 在渲染进程上下文中运行，但有 Node.js 权限    │
│  - 使用 contextBridge 将受控 API 暴露给渲染层  │
│  - 文件：electron/preload/index.ts           │
└──────────────┬──────────────────────────────┘
               │ window.electronAPI
┌──────────────▼──────────────────────────────┐
│          渲染进程 (Renderer Process)           │
│  - 标准浏览器环境：React + TypeScript         │
│  - 无 Node.js 能力（nodeIntegration: false）  │
│  - 通过 window.electronAPI 调用主进程          │
│  - 文件：src/ 目录                            │
└─────────────────────────────────────────────┘
```

**各进程职责划分：**

| 进程 | 职责 | 关键文件 |
|------|------|---------|
| 主进程 | 文件IO、向量化计算、LLM调用、子进程管理 | `electron/main/` |
| 预加载 | 安全桥接，将主进程能力以受控方式暴露 | `electron/preload/index.ts` |
| 渲染进程 | UI 渲染、用户交互、状态管理 | `src/` |

### 1.2 技术选型对比

#### 为什么用 Electron 而非 Tauri / 纯 Web？

| 对比维度 | Electron | Tauri | 纯 Web |
|---------|---------|-------|--------|
| 本地文件访问 | Node.js fs，完整支持 | Rust 命令，有限制 | 仅 File System Access API |
| ONNX 模型运行 | onnxruntime-node，完整支持 | 复杂，需 Rust 绑定 | onnxruntime-web，有 WASM 限制 |
| MCP 子进程 | stdio 子进程，原生支持 | 可行但复杂 | 不支持 |
| 生态 | 成熟，npm 全量可用 | 成熟但生态较小 | 受浏览器沙箱限制 |
| 包体积 | 较大（~150MB） | 小（~10MB） | N/A |
| **选择原因** | **需要完整 Node.js + 子进程支持** | | |

> 核心原因：MCP 需要 stdio 子进程通信，ONNX 模型需要 Node.js 运行时，这两点决定了必须使用 Electron。

#### 为什么用 Zustand 而非 Redux？

| 对比维度 | Zustand | Redux Toolkit |
|---------|---------|--------------|
| 包体积 | ~1KB | ~50KB |
| 样板代码 | 极少，直接定义 store | 需要 slice、reducer、action |
| 异步处理 | 在 action 中直接 async/await | 需要 thunk/saga 中间件 |
| TypeScript | 自动推导，零配置 | 需要额外类型标注 |
| 持久化 | persist 中间件，3行代码搞定 | redux-persist，配置复杂 |
| 选择器 | 函数式选择器，自动精确订阅 | useSelector + memoize |

#### 为什么用 Orama 而非 Faiss / Chroma？

| 对比维度 | Orama | Faiss | Chroma |
|---------|-------|-------|--------|
| 运行环境 | 纯 JS，主进程直接运行 | 需要编译原生模块 | 需要 Python 服务端 |
| 混合检索 | 内置 BM25 + 向量，一体化 | 仅向量检索 | 支持但配置复杂 |
| 无服务器 | 完全 in-process | 完全 in-process | 需要启动服务 |
| 本地优先 | JSON 序列化，直接落盘 | 二进制索引文件 | 数据库文件 |

#### 为什么用 Transformers.js 而非调用云端 Embedding API？

- **隐私优先**：书籍内容不离开本地，全程离线
- **无延迟**：本地推理无网络 RTT
- **成本**：无 API 调用费用
- **ONNX q8 量化**：模型文件从 ~90MB 压缩到 ~23MB，内存占用降低 75%

### 1.4 面试问答

**Q：渲染进程为什么不能直接访问文件系统？**

A：安全隔离。Electron 渲染进程本质是一个 Chromium 网页，默认运行在沙箱中，启用 `nodeIntegration: false` 后不具备任何 Node.js 能力。这防止了 XSS 攻击或恶意脚本通过渲染进程直接读写本地文件。文件操作必须通过 contextBridge 暴露的受控 API 经由预加载脚本转发到主进程执行，主进程再将结果通过 IPC 返回。

**Q：项目最大的技术难点是什么？**

A：端侧 RAG 在性能和用户体验之间的平衡。向量化一本 100 万字的小说需要对数千个文本块逐一计算 384 维向量，这在渲染进程中会完全冻结 UI。我们的解决方案是将 RAG 引擎放在 Electron 主进程（Node.js 环境）中运行，并设计了两阶段索引策略：先用不到 1 秒建立词法索引让书立刻可用，再后台异步升级语义向量索引，通过进度事件实时推送给 UI，完全不阻塞用户操作。

**Q：Local-First 架构有什么好处和挑战？**

A：好处是隐私完全可控、离线可用、无使用成本。挑战是向量索引需要本地存储和计算资源，我们用 SHA-256 内容哈希作为缓存键避免重复计算，用 q8 量化模型降低模型大小，用 LRU 策略限制内存中最多保留 5 个 Orama 索引，在性能和资源消耗之间取得平衡。

## 模块二：IPC 进程通信

### 2.1 contextBridge 安全隔离模型

contextBridge 是 Electron 的安全核心机制，在预加载脚本中运行，将主进程能力以"白名单"方式暴露给渲染进程，完全隔离 Node.js 环境：

```typescript
// electron/preload/index.ts
import { contextBridge, ipcRenderer } from 'electron'

const electronAPI: ElectronAPI = {
  mcp: {
    connect: (path: string): Promise<void> =>
      ipcRenderer.invoke('mcp:connect', path),
    // ... MCP 操作
  },
  llm: {
    chat: (messages, config) => ipcRenderer.invoke('llm:chat', messages, config),
    onChunk: (callback): (() => void) => {
      const listener = (_: unknown, chunk: string): void => callback(chunk)
      ipcRenderer.on('llm:chat-chunk', listener)
      return () => ipcRenderer.removeListener('llm:chat-chunk', listener)
    },
    onError: (callback): (() => void) => {
      const listener = (_: unknown, err: { code: string; message: string }): void => callback(err)
      ipcRenderer.on('llm:chat-error', listener)
      return () => ipcRenderer.removeListener('llm:chat-error', listener)
    },
    onChatComplete: (callback): (() => void) => {
      const listener = (_: unknown, data: { totalDuration: number }): void => callback(data)
      ipcRenderer.on('llm:chat-complete', listener)
      return () => ipcRenderer.removeListener('llm:chat-complete', listener)
    },
    cancelChat: (): void => {
      ipcRenderer.removeAllListeners('llm:chat-chunk')
      ipcRenderer.removeAllListeners('llm:chat-error')
      ipcRenderer.removeAllListeners('llm:chat-complete')
    },
  },
  // ...
}

contextBridge.exposeInMainWorld('electronAPI', electronAPI)
// 渲染进程通过 window.electronAPI.xxx() 调用
```

**关键安全设计**：
- contextBridge 创建了一个**结构化克隆边界**，渲染进程拿到的是代理对象，而非真实的 Node.js 函数引用
- 渲染进程无法访问 `ipcRenderer` 对象本身，只能通过预定义的函数调用
- 每个函数都是显式声明的白名单，不存在"任意调用"漏洞
- `cancelChat` 必须同时移除 `llm:chat-chunk`、`llm:chat-error`、`llm:chat-complete` 三个监听器，防止内存泄漏

### 2.2 三种 IPC 通信模式

项目中使用了 Electron IPC 的三种不同模式，根据场景选择：

#### 模式一：`invoke / handle`（双向请求-响应）
适用于需要等待返回值的操作：

```typescript
// 渲染进程（通过 preload 封装）
const files = await window.electronAPI.mcp.listFiles(path)
// ipcRenderer.invoke('mcp:list-files', path) → 等待 Promise 解析

// 主进程
ipcMain.handle('mcp:list-files', async (_, path) => {
  return await mcpManager.listFiles(path)
})
```

#### 模式二：`send / on`（单向推送，渲染→主进程）
适用于触发后台任务不需要立即返回：

```typescript
// 渲染进程：触发 RAG 索引（fire-and-forget），传入 AbortSignal 支持取消
const controller = new AbortController()
ipcRenderer.send('rag:ingest', { bookId, paragraphs })
// 取消：ipcRenderer.send('rag:cancel', bookId)
ipcMain.on('rag:ingest', async (event, { bookId, paragraphs }) => {
  // 后台异步处理，通过 event.sender.send 推送进度
})

// rag:cancel 实现：通过 AbortController.abort() 停止正在进行的索引
ipcMain.on('rag:cancel', (_, bookId: string) => {
  const controller = abortControllers.get(bookId)
  if (controller) controller.abort()
})
```

#### 模式三：主进程→渲染进程的事件推送
适用于长时任务的进度通知（LLM流式输出、RAG进度）：

```typescript
// 主进程：逐 token 推送
for await (const chunk of stream) {
  event.sender.send('llm:chat-chunk', content)
}
event.sender.send('llm:chat-complete', { totalDuration: Date.now() - startTime })

// 渲染进程（preload 封装）：分别注册 chunk、error、complete 监听
onChunk: (callback) => { /* ... */ },
onError: (callback) => {
  const listener = (_: unknown, err: { code: string; message: string }) => callback(err)
  ipcRenderer.on('llm:chat-error', listener)
  return () => ipcRenderer.removeListener('llm:chat-error', listener)
},
onChatComplete: (callback) => {
  const listener = (_: unknown, data: { totalDuration: number }) => callback(data)
  ipcRenderer.on('llm:chat-complete', listener)
  return () => ipcRenderer.removeListener('llm:chat-complete', listener)
},
```

### 2.3 类型安全四层同步

项目通过四个文件确保 IPC 类型一致性，任何一层改动都会导致 TypeScript 报错：

```
src/shared/types/index.ts          ← 定义所有数据结构（Message、LlmConfig 等）
         ↓ import
electron/main/ipc-handlers.ts      ← 主进程注册 handler，类型必须匹配
         ↓ 同步
electron/preload/index.ts          ← preload 封装，类型签名必须一致
         ↓ 同步
src/shared/types/electron.d.ts     ← 声明 window.electronAPI 的全局类型
```

```typescript
// src/shared/types/electron.d.ts
interface ElectronAPI {
  mcp: {
    connect: (path: string) => Promise<void>
    listFiles: (path: string) => Promise<BookFile[]>
    // ...
  }
  llm: {
    chat: (messages: Message[], config: LlmConfig) => Promise<void>
    onChunk: (callback: (chunk: string) => void) => () => void
    onError: (callback: (err: { code: string; message: string }) => void) => () => void
    onChatComplete: (callback: (data: { totalDuration: number }) => void) => () => void
    cancelChat: () => void
  }
}
declare global {
  interface Window {
    electronAPI: ElectronAPI
  }
}
```

### 2.5 面试问答

**Q：nodeIntegration 为什么默认关闭？**

A：nodeIntegration 开启后，渲染进程中的任何 JavaScript 代码（包括来自 `<script>` 标签或 XSS 注入的代码）都能直接调用 `require('fs')`、`require('child_process')` 等 Node.js API，这意味着一次 XSS 攻击就能读写任意本地文件甚至执行系统命令。关闭 nodeIntegration 并使用 contextBridge 是 Electron 官方安全最佳实践，只暴露明确声明的 API 白名单。

**Q：contextBridge 和直接在 window 上挂属性有什么区别？**

A：在预加载脚本中直接写 `window.myApi = { ... }` 也能工作，但存在安全隐患：渲染进程可以通过 prototype pollution 等方式篡改这些对象。contextBridge.exposeInMainWorld 会创建一个**深度冻结的结构化克隆代理**，渲染进程无法修改或访问其原型链，是更安全的暴露方式。

**Q：IPC invoke 和 send 怎么选？**

A：需要返回值就用 `invoke/handle`（Promise 风格，有 reject 错误传播）；只是触发操作不需要等待结果就用 `send/on`（fire-and-forget）。比如 RAG 索引是后台任务，触发后通过进度事件推送状态，用 `send` 更合适；而文件读取需要返回内容，用 `invoke`。

## 模块三：MCP 模块

### 3.1 MCP 协议概念

MCP（Model Context Protocol）是 Anthropic 推出的开放标准，定义了 AI 模型如何与外部工具/数据源交互的通信协议。核心思想是：

```
AI Client（LLM Agent）  ←→  MCP Server（工具/数据提供方）
```

在 ImmerseAI 中：
- **MCP Client**：`McpManager`，运行在 Electron 主进程
- **MCP Server**：`@modelcontextprotocol/server-filesystem`，提供本地文件系统操作能力
- **传输层**：`StdioClientTransport`，通过标准输入/输出与 Server 子进程通信

使用 MCP 而非直接用 `fs` 模块的核心优势是**协议标准化**——未来可以轻松替换成网络 MCP Server、数据库 MCP Server 等，不需要改动上层逻辑。

### 3.2 McpManager 单例实现

```typescript
// electron/main/mcp-manager.ts
export class McpManager {
  private static instance: McpManager | null = null
  private client: Client | null = null
  private transport: StdioClientTransport | null = null
  private status: ConnectionStatus = 'disconnected'

  // 私有构造函数，禁止 new McpManager()
  private constructor() {}

  // 全局唯一入口
  public static getInstance(): McpManager {
    if (!McpManager.instance) {
      McpManager.instance = new McpManager()
    }
    return McpManager.instance
  }
}
```

**为什么必须单例？**

MCP 连接会启动一个 `@modelcontextprotocol/server-filesystem` 子进程。如果允许多实例，每次 IPC 调用都可能创建新的子进程，导致：
1. 进程资源泄漏（大量僵尸子进程）
2. 多个子进程竞争访问同一文件夹
3. 应用退出时无法正确清理所有子进程

单例确保整个应用生命周期内只有一个 MCP 连接和一个子进程。

### 3.3 StdioClientTransport 通信机制

```
Electron 主进程                    MCP Server 子进程
┌────────────────┐  stdin (JSON-RPC req)  ┌──────────────────────┐
│ McpManager     │ ─────────────────────→ │ server-filesystem    │
│ (MCP Client)   │ ←───────────────────── │ (Node.js subprocess) │
└────────────────┘  stdout (JSON-RPC res) └──────────────────────┘
```

**开发模式 vs 打包模式的不同启动方式：**

```typescript
function getMcpServerConfig(localPath: string) {
  if (app.isPackaged) {
    // 打包模式：使用预先 esbuild 打包的独立 bundle
    // ELECTRON_RUN_AS_NODE=1 让 Electron 以纯 Node.js 模式运行
    const serverPath = path.join(process.resourcesPath, 'mcp-server.mjs')
    return {
      command: process.execPath,   // Electron 可执行文件自身
      args: [serverPath, localPath],
      env: { ...process.env, ELECTRON_RUN_AS_NODE: '1' },
    }
  } else {
    // 开发模式：npx 直接拉起
    return {
      command: 'npx',
      args: ['-y', '@modelcontextprotocol/server-filesystem', localPath],
    }
  }
}
```

### 3.4 指数退避重试策略

```typescript
const RETRY_DELAYS = [2000, 4000, 8000]  // 2s → 4s → 8s
const MAX_RETRIES = 3

private async connectWithTimeout(timeoutMs = 10000): Promise<void> {
  return Promise.race([
    this._doConnect(),
    new Promise<void>((_, reject) =>
      setTimeout(() => reject(new Error('MCP handshake timeout')), timeoutMs)
    ),
  ])
}

private async _attemptConnection(localPath: string, retryCount = 0): Promise<void> {
  try {
    await this.connectWithTimeout()
    this.status = 'connected'
  } catch (error) {
    if (retryCount < MAX_RETRIES) {
      // 清理失败的连接尝试
      this.client = null
      this.transport = null
      // 等待退避时间后递归重试
      await new Promise(resolve => setTimeout(resolve, RETRY_DELAYS[retryCount]))
      return this._attemptConnection(localPath, retryCount + 1)
    } else {
      // 重试耗尽，分类错误并抛出
      this.status = 'error'
      throw new McpConnectionError(message, errorCode, 0)
    }
  }
}
```

**为什么用指数退避而不是固定间隔？**

子进程启动失败往往是系统资源短暂紧张（如 npm 缓存更新、杀毒软件扫描），短暂等待后通常能恢复。指数退避避免了在系统繁忙时频繁重试加重负担，同时总重试时间（2+4+8=14s）对用户感知可接受。

  errorCode = 'SPAWN_FAILED'       // npx 找不到、命令不存在
} else if (errorMessage.includes('timeout') || errorMessage.includes('Timeout')) {

### 3.6 面试问答

**Q：MCP 和直接用 Node.js fs 模块有什么区别，为什么不直接用 fs？**

A：直接用 fs 和 MCP 在功能上确实等价，但设计理念不同。MCP 是工具调用的标准协议，它的价值在于：第一，标准化——将来如果 Agent 需要读取数据库、调用外部 API，只需切换 MCP Server，Client 代码不变；第二，可扩展性——MCP Server 可以运行在任何地方，包括远程服务器；第三，工具发现——Client 可以动态查询 Server 支持哪些工具（`listTools`），不需要硬编码。项目中选择 MCP 是为了架构上的前瞻性和 AI Agent 范式的实践。

**Q：单例模式有什么缺点，如何测试？**

A：单例模式最大的缺点是难以测试（全局状态污染）和难以替换（强耦合）。测试时我们通过在 `McpManager.instance` 上注入 mock 对象来解决。在生产代码中，单例的好处（确保唯一子进程）远大于其缺点，且 Electron 主进程本身就是单进程，单例在这个上下文非常自然。

**Q：子进程崩溃了怎么办？**

A：`StdioClientTransport` 会监听子进程的 `close` 事件，崩溃时会触发错误，`McpManager` 将状态更新为 `error`，并通过 IPC 通知渲染进程显示错误提示。用户可以通过重新点击"连接书库"按钮触发重连，这时 `connectLocal` 会检测到 `error` 状态并重新发起连接（含重试逻辑）。

## 模块四：RAG 引擎

### 4.1 RAG 概念与端侧挑战

**RAG（Retrieval-Augmented Generation）**：在向 LLM 提问前，先从知识库中检索最相关的文本片段，将其作为上下文拼入 Prompt，让 LLM 基于真实内容作答，而非依赖训练参数记忆。

**端侧 RAG 的三大挑战：**

1. **计算瓶颈**：向量化（Embedding）需要运行神经网络，CPU 推理一本 100 万字小说约需 5~30 分钟
2. **环境限制**：浏览器渲染进程受 `file://` 协议限制，无法加载本地 ONNX 模型文件
3. **内存限制**：大书籍的向量索引可达数百 MB，需要精细的内存管理

**解决方案：**

| 挑战 | 解决方案 |
|------|---------|
| 计算瓶颈 | 两阶段索引：先词法（<1s）再后台语义升级 |
| 环境限制 | 迁移到主进程（Node.js），规避 file:// 限制 |
| 内存限制 | LRU 限制最多 5 个 Orama 索引 + SHA-256 磁盘缓存 |

### 4.2 嵌入模型

**为什么选 all-MiniLM-L6-v2？**

- 384 维平衡了精度与计算速度
- 在 MTEB（文本嵌入基准）上排名靠前的小模型
- ONNX 量化版本约 23MB，适合打包进桌面应用

### 4.3 自适应分块策略

不同规模的书籍采用不同的分块粒度，避免"一刀切"导致短文切太细或长篇切太粗：

```typescript
// electron/main/rag-handler.ts
export function adaptiveChunkSize(totalChars: number): { chunkSize: number; chunkOverlap: number } {
  let chunkSize: number
  if (totalChars < 200_000)      chunkSize = 500   // 短文/短篇
  else if (totalChars < 2_000_000)  chunkSize = 1_000  // 中长篇小说
  else if (totalChars < 10_000_000) chunkSize = 2_000  // 长篇小说
  else                              chunkSize = 4_000  // 超长网文

  chunkSize = Math.min(Math.max(chunkSize, 500), 8_000)  // clamp [500, 8000]
  const chunkOverlap = Math.max(50, Math.floor(chunkSize * 0.1))  // 10% 重叠
  return { chunkSize, chunkOverlap }
}
```

**分块算法（递归分隔符）：**

```typescript
const BATCH_SIZE = 64  // 向量化批处理大小（曾为 32）

const separators = ['\n\n', '\n', '。', '！', '？', ' ']
// 优先按段落分，再按句子分，最后按字符硬切
// 相邻 chunk 保留 10% 重叠，避免语义在边界处被截断
// 使用数组拼接而非字符串追加，避免 O(n²) 性能问题
```

**为什么要重叠（overlap）？**

如果一个完整的句子恰好跨越两个 chunk 的边界，没有重叠会导致两个 chunk 都无法完整表达这个句子的语义。10% 的重叠确保语义完整性，代价是略微增加索引大小。

### 4.4 两阶段索引设计

这是 RAG 引擎最核心的工程设计，解决大书籍索引慢的用户体验问题：

```
书籍加载
    │
    ├─ Phase 1 (立即完成, < 1s)
    │   建立 Orama BM25 词法索引
    │   书籍状态立刻变为"可用"
    │   用户可以开始聊天（词法搜索）
    │
    └─ Phase 2 (后台异步, 5~30分钟)
        仅对 chunks > 5000 的超大书籍触发

        实时推送 rag:upgrade-progress 进度事件
        完成后书籍升级为混合检索模式
```

**两阶段触发阈值：**

```typescript

### 4.5 混合检索与 RRF 融合

```
用户查询 "林黛玉为什么哭"
    │
    ├─ 语义路径（Semantic）
    │   query → embedding([384维向量])
    │   与所有有 embedding 的 chunk 计算 cosine 相似度
    │   取 top topK×2 = 10 个结果，按排名打分
    │
    └─ 词法路径（Lexical）
        Orama BM25 全文检索
        对所有 chunks 进行关键词匹配
        取 top topK×2 = 10 个结果，按排名打分
            │
            ▼
        RRF 融合排名（Reciprocal Rank Fusion）
        score(d) = Σ 1/(k + rank_i(d))  k=60
        合并排名，输出最终 top K 结果
```

**RRF 公式：**

```typescript
const RRF_K = 60  // 学术标准默认值，平衡高排名和低排名的影响

// 每个结果的贡献 = 1 / (60 + rank + 1)
// rank=0 贡献 1/61 ≈ 0.0164
// rank=9 贡献 1/70 ≈ 0.0143
// 两路都命中同一文档，分数叠加，排名靠前

scoreMap.forEach((item, rank) => {
  const contribution = 1 / (RRF_K + rank + 1)
  existing.score += contribution  // 累加两路得分
})
```

**为什么混合检索效果更好？**

- **纯语义**：理解概念相似性，但对专有名词（人名、地名）不敏感
- **纯词法**：精确匹配关键词，但不理解同义词和语义关联
- **混合**：两路互补，对"林黛玉"这样的专有名词词法匹配精准，对"为什么哭"这样的情感语义则向量匹配更好

### 4.6 SHA-256 内容哈希缓存

```typescript
// 缓存键：书籍内容的 SHA-256 哈希，与文件路径无关
export function computeContentHash(paragraphs: RagParagraph[]): string {
  const content = paragraphs.map(p => p.text).join('\n')
  return crypto.createHash('sha256').update(content, 'utf8').digest('hex')
}

// 缓存存储：userData/rag-cache/{contentHash}.json
function getCachePath(contentHash: string): string {
  return path.join(app.getPath('userData'), 'rag-cache', `${contentHash}.json`)
}
```

**为什么用内容哈希而非文件路径？**

用户整理书库时经常重命名文件或移动文件夹。基于路径的缓存会在每次移动后失效，导致重复索引。基于内容哈希，只要书籍内容不变，无论文件怎么移动都命中缓存，避免重复计算。

**缓存版本控制：**

```typescript
const CACHE_VERSION = 3

// 读取缓存时检查版本
if (data.version !== CACHE_VERSION) {
  // 旧版本缓存自动淘汰，重新建立索引
  await fsAsync.unlink(getCachePath(contentHash))
  return null
}
```

### 4.7 面试问答

**Q：RRF 是什么？k=60 怎么选的？**

A：RRF（Reciprocal Rank Fusion）是一种融合多路排名结果的算法，核心公式是 `score = Σ 1/(k + rank)`。每个结果在某路检索中的排名越靠前，贡献越大；两路都命中的结果分数叠加，天然实现"两路认可的结果排名更靠前"的效果。k=60 是 2009 年原始论文的推荐默认值，大量实验证明在 50~80 范围内效果差异不大，60 已成为业界惯例。

**Q：为什么 RAG 不放在 Web Worker 而是主进程？**

A：最初确实考虑过 Web Worker，但有两个无法绕过的问题：第一，渲染进程（包括 Worker）运行在 `file://` 协议下，`@huggingface/transformers` 在加载 ONNX 模型时需要通过路径读取本地文件，`file://` 协议有严格的跨域限制，导致模型加载失败；第二，Worker 中 `fetch` 和 `XMLHttpRequest` 对本地文件的支持不稳定。迁移到主进程后，Node.js 的 `fs` 模块直接读取模型文件，问题彻底解决。

**Q：如果用户的书非常大，索引期间应用卡吗？**

A：不卡。索引运行在主进程，与渲染进程是独立的 V8 实例，不会阻塞 UI 渲染。两阶段设计保证了第一阶段（词法索引）在 1 秒内完成，书籍立刻可用；第二阶段（语义升级）完全后台运行，通过进度事件实时通知 UI 展示进度条，用户可以正常使用应用。

### 5.4 JSON 解析兜底策略

LLM 有时会在 JSON 前后添加解释文字或用 markdown 代码块包裹，直接 `JSON.parse` 会失败：

```typescript
function parsePersonaJson(response: string): Persona | null {
  // 第一步：尝试直接解析
  try {
    return JSON.parse(response.trim())
  } catch {}

  // 第二步：移除 markdown 代码块
  const codeBlock = response.match(/```(?:json)?\s*([\s\S]+?)\s*```/)
  if (codeBlock) {
    try { return JSON.parse(codeBlock[1]) } catch {}
  }

  // 第三步：正则提取第一个 {...} 块（兜底）
  const jsonMatch = response.match(/\{[\s\S]+\}/)
  if (jsonMatch) {
    try { return JSON.parse(jsonMatch[0]) } catch {}
  }

  return null  // 生成失败，返回 null
}
```

### 5.6 面试问答

**Q：temperature 为什么设 0.3 而不是 0 或 1？**

A：temperature 控制 LLM 输出的随机性。temperature=0 完全确定性，每次生成相同角色描述，但描述会显得机械；temperature=1 创造性很强，但可能偏离书中原著描述。0.3 是一个经验值平衡点：既能忠实于原著内容（RAG 上下文约束），又能有适当的语言润色让描述更自然流畅。而意图识别用 temperature=0.1 是因为我们需要确定性的 JSON 输出，创造性反而是干扰。

**Q：如果书还没建立索引就点击生成角色怎么办？**

A：`generatePersona` 第一步会调用 `checkBookIndexedStatus`，检查该书的 `contentHash` 是否已有缓存。如果没有，会先触发 `window.electronAPI.rag.ingest` 建立索引，等待 `ingest-complete` 事件后再继续生成。整个过程对用户透明，UI 显示"正在建立索引..."的加载状态。

## 模块六：LLM 流式对话

### 6.1 流式架构设计

流式输出（Streaming）让 LLM 每生成一个 token 就立刻推送给用户，而非等全部生成完才显示，大幅提升感知响应速度。

```
OpenAI API (SSE)
    │ for await (const chunk of stream)
    ▼
主进程 LlmHandler
    │ event.sender.send('llm:chat-chunk', content)
    ▼
IPC 推送
    │ ipcRenderer.on('llm:chat-chunk', listener)
    ▼
预加载 Preload
    │ callback(chunk)
    ▼
渲染进程 ReadableStream
    │ controller.enqueue(chunk)
    ▼
useChat.ts
    │ reader.read() 循环消费
    ▼
React State 更新
    │ setCurrentMessage(prev => prev + chunk)
    ▼
MessageBubble 逐字渲染（打字机效果）
```

### 6.2 ReadableStream 封装

关键设计：**先注册监听，再触发请求**，确保不丢失任何 chunk：

```typescript
// src/shared/utils/llm-stream.ts
export function createLlmStream(messages: Message[], config: LlmConfig): ReadableStream<string> {
  return new ReadableStream<string>({
    start(controller) {
      // 1. 先注册完成监听（事件驱动，不遗漏）
      const removeComplete = window.electronAPI.llm.onChatComplete(() => {
        removeComplete()
        removeChunk()
        removeError()
        controller.close()    // 正常终止流
      })

      // 2. 注册 chunk 监听
      const removeChunk = window.electronAPI.llm.onChunk((chunk) => {
        controller.enqueue(chunk)  // 推入队列
      })

      // 3. 注册错误监听
      const removeError = window.electronAPI.llm.onError((err) => {
        removeComplete()
        removeChunk()
        removeError()
        controller.error(new Error(err.message))  // 以错误终止流
      })

      // 4. 最后发起请求（此时监听已就绪，不会丢失 chunk）
      window.electronAPI.llm.chat(messages, config).catch((e: Error) => {
        removeComplete()
        removeChunk()
        removeError()
        controller.error(e)
      })
    },

    // 用户取消时（如点击"停止生成"）
    cancel() {
      window.electronAPI.llm.cancelChat()
      // cancelChat 实现：removeAllListeners('llm:chat-chunk') + 'llm:chat-error' + 'llm:chat-complete'
    },
  })
}
```

### 6.3 主进程流式输出

```typescript
// electron/main/llm-handler.ts
export async function handleLlmChat(event, messages, config): Promise<void> {
  const client = getOrCreateClient(apiKey, baseUrl)
  const startTime = Date.now()

  // stream: true 开启 SSE 流式模式
  const stream = await client.chat.completions.create({
    model, messages: openaiMessages,
    stream: true, temperature, max_tokens: maxTokens,
  })

  // 逐 chunk 发送，检查渲染进程是否仍然存在
  for await (const chunk of stream) {
    if (event.sender.isDestroyed()) break  // 渲染进程已关闭，停止发送

    const content = chunk.choices[0]?.delta?.content
    if (content) {
      event.sender.send('llm:chat-chunk', content)
    }
  }

  if (!event.sender.isDestroyed()) {
    event.sender.send('llm:chat-complete', { totalDuration: Date.now() - startTime })
  }
}
```

  if (cachedClient && cachedClient.configHash === hash) {
    return cachedClient.client  // 配置未变，复用 client（含连接池）
  }

  const client = new OpenAI({ apiKey, baseURL: baseUrl, maxRetries: 2, timeout: 30000 })
  cachedClient = { client, configHash: hash }
  return client

### 6.4 useChat 核心流程

```typescript
// src/features/chat/hooks/useChat.ts（简化版）
async function sendMessage(text: string) {
  setIsGenerating(true)

  // Step 1: 检测笔记意图（纯正则，零延迟）
  const noteIntent = detectNoteIntent(text)
  if (noteIntent.isNote) {
    await handleNoteFlow(text, noteIntent)
    return
  }

  // Step 2: RAG 检索相关段落（topK=5）
  const ragResults = await window.electronAPI.rag.search(contentHash, text, 5)

  // Step 3: 构建 LLM messages（system prompt 注入 RAG 上下文）
  const messages = buildChatMessages(persona, ragResults, history, text)

  // Step 4: 创建流并逐字渲染
  const stream = createLlmStream(messages, llmConfig)
  const reader = stream.getReader()
  let fullText = ''

  try {
    while (true) {
      const { done, value } = await reader.read()
      if (done) break
      fullText += value
      // 实时更新消息内容（React 状态更新触发重渲染）
      updateLastMessage(fullText)
    }
  } finally {
    reader.releaseLock()
    setIsGenerating(false)
    saveMessage({ role: 'assistant', content: fullText, citations: ragResults })
  }
}

### 6.6 面试问答

**Q：流式渲染和非流式有什么本质区别？怎么实现打字机效果？**

A：非流式是等 LLM 生成完所有内容后一次性返回，用户看到一段漫长的空白然后全文突然出现，体验很差。流式是 Server-Sent Events（SSE），LLM 每生成一个 token 就立刻推送，用户看到文字一字一字地出现，感知延迟从"全部生成时间"降为"第一个 token 时间"（通常<1s）。打字机效果的实现：每收到一个 chunk，用 `setState(prev => prev + chunk)` 追加到消息尾部，React 的 concurrent 模式会自动批处理高频状态更新，避免性能问题。

**Q：流传输中如何处理取消操作？**

A：用户点击"停止"时调用 `stream.cancel()`，这会触发 ReadableStream 的 `cancel()` 钩子，里面调用 `window.electronAPI.llm.cancelChat()`，preload 中的 cancelChat 实现是 `removeAllListeners('llm:chat-chunk')`，移除所有 chunk 监听器。主进程虽然仍在继续流式接收 OpenAI 的响应，但已经没有人监听了，事件会被丢弃。同时我们在 `useChat` 的 cleanup 中调用 `reader.cancel()`，释放流资源，将当前已接收的部分内容保存为完整消息。

**Q：为什么先注册监听再触发请求，顺序重要吗？**

A：非常重要。如果先 `invoke('llm:chat')` 再注册监听，存在一个竞态窗口：主进程可能在监听注册完成前就开始发送第一批 chunks，这些 chunks 会被静默丢弃，导致输出不完整或乱码。先注册监听确保消息通道在请求发出前就已就绪，不会丢失任何 token。

### 7.5 useRef 防止 stale closure

在 `useRag.ts` 中，回调函数注册到 IPC 监听器后，如果用 `useEffect` 中捕获的回调，可能拿到过期的闭包引用：

```typescript
// src/shared/hooks/useRag.ts
export function useRag(options: UseRagOptions): UseRagResult {
  // 用 useRef 保存最新的回调引用，避免 stale closure
  const onIngestProgressRef = useRef(options.onIngestProgress)
  const onIngestCompleteRef = useRef(options.onIngestComplete)

  // 每次 render 更新 ref（不触发重渲染）
  useEffect(() => {
    onIngestProgressRef.current = options.onIngestProgress
    onIngestCompleteRef.current = options.onIngestComplete
  })

  useEffect(() => {
    // 注册 IPC 监听器，使用 ref 的值，始终是最新的回调
    const removeProgress = window.electronAPI.rag.onIngestProgress((data) => {
      onIngestProgressRef.current?.(data)  // 通过 ref 调用，永远不过期
    })

    const removeComplete = window.electronAPI.rag.onIngestComplete((data) => {
      onIngestCompleteRef.current?.(data)
    })

    // 组件卸载时取消所有监听，防止内存泄漏
    return () => {
      removeProgress()
      removeComplete()
    }
  }, [])  // 空依赖数组，只注册一次
}
```

**stale closure 问题说明**：如果直接在 `useEffect` 的依赖数组中加入 callback，每次父组件重渲染传入新函数引用时，会导致 `useEffect` 重新执行，取消旧监听再注册新监听——这对 IPC 监听器来说是不必要的开销，也可能导致短暂的事件丢失。`useRef` 模式彻底解决这个问题。

### 7.6 面试问答

**Q：为什么不用 React Context + useReducer？**

A：Context + useReducer 在这个场景有两个明显缺陷：第一，性能问题——Context 的任何值变化都会导致所有消费该 Context 的组件重渲染，无法精确订阅某个字段；第二，跨组件通信繁琐——需要将 Context 层层传递或设置多个 Context。Zustand 的 selector 模式天然支持精确订阅，任何组件都可以直接订阅需要的字段，不需要传递 Provider。

**Q：Zustand 的 set 函数是同步还是异步的？**

A：`set` 是同步执行的，立即更新 store 状态并触发订阅该状态的组件重渲染。但 React 的渲染是异步批处理的，在事件处理函数中多次调用 `set` 会被批处理成一次渲染。如果需要在 `set` 后立即读取更新后的值，应该用 `useStore.getState()` 而非 `useStore()` hook。

## 模块八：Librarian Agent（AI 书架管理）

### 8.1 Agent 架构

Librarian 是一个轻量级的工具调用 Agent，将自然语言指令转化为文件系统操作：

```
用户输入："把科幻类书籍移到科幻文件夹"
    │
    ▼
Step 1: 意图识别（LLM，temperature=0.1）
    输入：用户消息 + 当前书架文件列表
    输出：JSON { intent: 'move_file', params: { source: '...', destination: '...' } }
    │
    ▼
Step 2: 工具路由（switch/case）
    list_files      → executeListFiles
    create_directory → executeCreateDirectory
    move_file       → executeMoveFile
    delete_file     → handleDeleteConfirmation（不直接执行！）
    unknown         → 返回错误提示
    │
    ▼
Step 3: 执行（调用 window.electronAPI.mcp.*）
    │
    ▼
Step 4: 反馈（更新 agentHistory，显示操作结果）
```

### 8.2 意图识别

```typescript
async function recognizeIntent(
  userMessage: string,
  fileList: BookFile[],
  llmConfig: LlmConfig
): Promise<IntentRecognitionResult> {
  const systemPrompt = buildLibrarianSystemPrompt(fileList)
  // system prompt 包含：
  // 1. 当前书架文件列表（给 LLM 上下文）
  // 2. 支持的操作及参数格式说明
  // 3. 严格要求输出 JSON 格式

  const stream = createLlmStream(
    [{ role: 'system', content: systemPrompt }, { role: 'user', content: userMessage }],
    { ...llmConfig, temperature: 0.1, maxTokens: 256 }
  )

  // 收集完整响应
  let response = ''
  const reader = stream.getReader()
  while (true) {
    const { done, value } = await reader.read()
    if (done) break
    response += value
  }

  return parseJsonResponse(response)
}
```

**为什么 temperature=0.1？**

意图识别要求输出严格的 JSON 格式，任何格式错误都会导致解析失败。temperature=0.1 让 LLM 几乎确定性地选择最可能的 token，大幅减少格式变异的概率。maxTokens=256 也足够，意图 JSON 通常只有几十个字符。

### 8.3 parseJsonResponse：markdown 代码块剥离

LLM 经常把 JSON 包裹在 markdown 代码块中：

```typescript
function parseJsonResponse(response: string): IntentRecognitionResult {
  let trimmed = response.trim()

  // 剥离 markdown 代码块
  if (trimmed.startsWith('```json')) trimmed = trimmed.slice(7)
  else if (trimmed.startsWith('```'))   trimmed = trimmed.slice(3)
  if (trimmed.endsWith('```'))          trimmed = trimmed.slice(0, -3)

  trimmed = trimmed.trim()

  try {
    const parsed = JSON.parse(trimmed)
    const validIntents = ['list_files', 'move_file', 'create_directory', 'delete_file', 'unknown']

    // 验证 intent 合法性，防止注入非法操作
    if (!validIntents.includes(parsed.intent)) {
      return { intent: 'unknown', params: {} }
    }

    return { intent: parsed.intent, params: parsed.params ?? {} }
  } catch {
    return { intent: 'unknown', params: {} }  // 解析失败降级为 unknown
  }
}
```

### 8.4 delete 二次确认保护

`delete_file` 是不可逆操作，必须经过用户二次确认，Agent 不能直接执行：

```typescript
async function handleDeleteConfirmation(params): Promise<AgentExecuteResult> {
  // 不执行删除！返回需要确认的信号
  return {
    success: false,
    message: `即将删除文件 "${fileName}"，此操作不可撤销`,
    operation: { intent: 'delete_file' },

    },

  await window.electronAPI.mcp.deleteFile(path)
  return { success: true, message: `已删除 "${fileName}"` }

```

**安全设计层次：**

1. **LLM 层**：validIntents 白名单验证，防止 prompt injection 注入非法意图
2. **路由层**：delete 意图永远路由到 `handleDeleteConfirmation`，不可绕过
3. **UI 层**：弹窗二次确认，用户必须主动点击
4. **MCP 层**：文件操作通过 MCP Server 执行，有文件系统权限边界

### 8.5 路径安全校验

防止相对路径穿越或操作书库根目录以外的文件：

```typescript
function isRootDirectChildPath(rootPath: string, targetPath: string): boolean {
  const normalizedRoot = normalizePath(rootPath).replace(/\/+$/, '')
  const normalizedTarget = normalizePath(targetPath).replace(/\/+$/, '')

  // 目标必须以根路径开头
  if (!normalizedTarget.startsWith(`${normalizedRoot}/`)) return false

  // 不允许跨层（只能操作直接子目录）
  const relative = normalizedTarget.slice(normalizedRoot.length + 1)
  if (!relative || relative.includes('/')) return false

  return true
}

// 创建目录时校验，防止在任意位置创建目录
if (intent === 'create_directory' && !isRootDirectChildPath(bookshelfPath, dirPath)) {
  return { success: false, message: '只能在书库根目录下创建文件夹' }
}

### 8.6 面试问答

**Q：如何防止 LLM 幻觉导致误删文件？**

A：多层防护：第一层，意图合法性校验——即使 LLM 输出了 `"intent": "format_disk"` 这样的幻觉内容，`validIntents` 白名单会将其转为 `unknown`，不执行任何操作；第二层，delete 永远触发二次确认弹窗，不管 LLM 多"确定"都需要用户手动确认；第三层，路径校验确保只操作书库目录内的文件；第四层，temperature=0.1 从概率上减少输出格式错误和幻觉。

**Q：这个 Agent 和 ReAct/Function Calling 框架有什么区别？**

A：这是一个简化的单轮意图识别 Agent，不是多轮 ReAct 循环。用户每次输入都经过一次"识别→执行→反馈"循环，不支持 Agent 自主多步规划。选择这个简化设计是因为书架管理操作都是原子性的单步操作（移动/删除/创建），不需要多步推理，简单设计更稳定、更可预测、更易于测试和调试。

  }
}

export function getSafeStorageValue(key: string): string | null {
  try {
    const base64 = store.get(key) as string
    const encrypted = Buffer.from(base64, 'base64')
    return safeStorage.decryptString(encrypted)
  } catch {
    return null
  }
}
```

**`safeStorage` 工作原理：**

- **Windows**：使用 DPAPI（Data Protection API），加密密钥与登录用户绑定，其他用户账户无法解密
- **macOS**：使用 Keychain，系统级安全存储
- **Linux**：使用 libsecret 或 kwallet

API Key 明文永远不写入磁盘，即使用户的配置文件被泄露，攻击者也无法获取 API Key。

}

### 9.7 面试问答

**Q：如何保护用户的 API Key？**

A：三层保护：第一，API Key 通过 `safeStorage.encryptString` 用系统级加密（Windows DPAPI / macOS Keychain）存储，明文不写磁盘；第二，Key 只在主进程使用，通过 IPC 只传递加密后的存储键名，渲染进程永远拿不到明文 Key；第三，在 `configHash` 计算时只取 Key 的前 8 位用于脏检测，日志中也不会出现完整 Key。

**Q：Electron 安全最佳实践有哪些？**

A：官方推荐的核心实践包括：第一，`nodeIntegration: false` + `contextIsolation: true`（默认），通过 contextBridge 暴露白名单 API；第二，`sandbox: true` 开启渲染进程沙箱；第三，不加载远程内容，只使用 `loadFile` 加载本地 HTML；第四，配置 Content Security Policy 防止 XSS；第五，使用 `safeStorage` 存储敏感数据；第六，定期更新 Electron 版本修复安全漏洞。ImmerseAI 严格遵循了这些实践。

**Q：项目中如何做代码质量保证？**

A：从三个维度：第一，TypeScript strict 模式 + `noImplicitAny`，编译时捕获大部分类型错误；第二，ESLint 配置了 `no-explicit-any`、`consistent-return`、`react-hooks/exhaustive-deps` 等规则，代码风格和 hooks 使用规范有静态检查保证；第三，模块间有清晰的职责边界——IPC 通道名和类型在四个文件中同步，任何不一致都会在编译时暴露，防止运行时 IPC 调用失败。

### 10.1 渐进式加载策略

大文档（>100万字）一次性加载会导致白屏等待体验极差。阅读器采用三阶段渐进式加载：

```
阶段1（立即，<100ms）
  └── 显示最后阅读位置 ± 10 段落，用户可立即阅读
阶段2（后台，异步）
  └── requestIdleCallback 让出主线程，分批加载全文段落
阶段3（完成）
  └── 全量内容缓存到内存，后续跳转即时响应
```

**最后阅读位置恢复**：通过 `Book.lastReadParagraphIndex` 持久化，每次打开书籍直接跳转到上次离开的位置。

```typescript
// useReader.ts
const lastReadIdx = book?.lastReadParagraphIndex ?? 0
